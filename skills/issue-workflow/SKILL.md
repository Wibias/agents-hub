# Issue Workflow

Use this skill for durable product, bug, triage, and refactor artifacts on the
project issue tracker. Prefer the project's domain language over file paths.

## Routing

| Request | Workflow |
|---|---|
| PRD | Synthesize context into a product requirements document |
| Issue breakdown | Convert plan/spec/PRD into vertical-slice tickets |
| Triage | Classify issues and move them through the tracker state model |
| QA intake | File user-reported bugs from a conversational QA session |
| Refactor request | Interview, verify codebase, produce tiny-commit refactor plan |

If the tracker mapping, labels, or domain layout are unknown, infer from repo context first. Ask only when publishing would be unsafe.

For full procedure steps, read `references/workflows.md`.

## Shared Rules

- Write durable artifacts that survive refactors.
- Avoid file paths and line numbers in issue bodies unless the user explicitly asks for a short-lived implementation note.
- Describe behavior and contracts, not step-by-step implementation.
- Use existing domain terms, glossary files, ADRs, and issue labels when present.
- Do not close or modify parent issues unless explicitly asked.
- Publish in dependency order when one issue must reference another.
- For tracker comments created during triage, start with:

  ```markdown
  > *This was generated by AI during triage.*
  ```

## Authority Invariant

**Default: all outputs are local drafts.** Never file, update, or close tracker items without explicit user authority. Durable recorded prior authority counts; one approval is enough. For full rules and Linear requirements, read `references/tracker-authority.md`.

## AFK / HITL

- Mark issue slices `AFK` when an agent can implement them without human judgment.
- Mark `HITL` when a design or product decision is still needed.
